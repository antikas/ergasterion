# Migrating an estate from 0.5 to 0.6

0.6.0 is a declared breaking release. The authoring surface changed: a 0.5 estate is
authored as source declarations plus a domain file per domain, and a 0.6 estate is authored
as source declarations plus one **product declaration** per published product. There are no
aliases, no shims and no compatibility readers. A 0.5 estate does not emit under 0.6 until
its declarations are rewritten.

This guide is the conversion. It states what maps mechanically, what a person has to decide,
and how to prove the result.

**On the worked examples in this guide.** No 0.5 estate remains in this repository: the
domain files, the legacy generated tree and the legacy route were removed when 0.6 landed.
No 0.5 fixture remains for these steps. The examples show declaration forms before and
after conversion. Every "after" form comes from a declaration under
`declarations/products/` that this repository emits.

## 1. What has to be true before you start

- **You are on a branch, and the 0.5 estate still builds.** You will be comparing results,
  and the 0.5 build is the thing you compare against.
- **Your 0.5 estate is committed, including its generated tree.** Nothing in 0.6 reads it,
  but you will want to read it yourself while you work.
- **You know which published relations matter.** The unit of a 0.6 declaration is a
  published product, so the conversion starts from what the estate publishes, not from what
  it computes on the way there.

Install the new line into a fresh environment. Keep the 0.5 environment available for the
comparison:

```bash
python -m venv .venv-06
source .venv-06/bin/activate
python -m pip install "ergasterion-factory[local-ingestion]"
```

## 2. Estate configuration comes first

0.5 held estate policy in several places, including inside domain files. 0.6 holds it in
`estate.yml`, and nothing emits until it is right.

Declare, in this order:

1. **The adapters.** Each one with a kind, `reference` or `deployment`, and one of them named
   as the `final_target`. The reference adapter is the one that executes your estate locally.
2. **The layer labels** your estate uses, and for each one the reference profiles it admits.
   A label admitting exactly one profile lets a product omit `profile`; a label admitting
   more than one requires it. Your 0.5 layer vocabulary is a fine starting point: it becomes
   labels, and the engine reads them only as keys.
3. **The translator table.** For each label, which translator renders each pattern and each
   shape. This is the entry the router looks up. A label with no entry for a pattern its
   profile carries fails closed at routing, naming the label, the pattern and the adapter,
   which is exactly the error you want while you are converting.
4. **The expression mode**, `sql` or `named_only`, and any structured types beyond the fixed
   neutral scalars.
5. **The estate namespace, support contact and owning team.** Every generated contract's
   ownership section is built from these three, and there is no engine default for any of
   them.

Per-adapter structural budgets and interface boundaries move out of the domain file and into
`declarations/targets/<adapter>.yml`, one document per adapter.

## 3. Source declarations: what changes, and what does not

A source declaration keeps its job. It still describes one source system's tables, columns
and types, and it is still the thing a landing product binds to.

Two things change inside it.

**Technology syntax goes.** A 0.5 `projection.expression` could carry a dbt or Jinja
expression, preserved as an explicit adapter extension. 0.6 rejects that in every
declaration. Replace each expression as follows:

- a plain SQL expression stays, as inline SQL, in the product that computes it;
- an expression with a dispatch macro, `ref(`, `source(`, a platform reference, or a file
  path becomes a **named rule**. Declare its signature once in the estate rule catalogue.
  Implement it per translator and per adapter where dialects differ.

**The layer label becomes explicit.** A table delivered in production declares the label it
lands under. The runtime route looks up that label in the translator table. It does not
infer the label from the resolved profile.

Both importers remain available when you seed a new source:

```bash
ergasterion import-odcs supplier-contract.yml --source supplier_name
ergasterion import-ddl source-tables.sql --source supplier_name
```

## 4. Domain files become product declarations

This is the substance of the conversion. A 0.5 domain file described a whole domain in
sections keyed by structure. A 0.6 estate has no domain file at all: each of those sections
becomes part of a product declaration, or an estate configuration entry, or nothing.

| 0.5 domain-file section | Where it goes in 0.6 |
|---|---|
| `entity_configs` payload rosters and hash columns | The `data_vault` shape's target block, on the product that publishes those stores. An estate not using that shape does not carry them at all. |
| `hub_configs`, `link_configs` | The `data_vault` shape's target block, on the same product. |
| `bv_configs` survivorship rules | The `survivorship` block of a Data Curation occurrence, one entry per attribute, on the integration product that publishes the curated entity. |
| `res_configs` match keys and columns | The `resolution` block of the same Data Curation occurrence: `strategy`, the ranked `keys`, and the record key. |
| `res_configs` model paths | Nothing. A product declares what it publishes; where a relation is written is the translator's business. |
| `odcs` block: contract version, status, products | The `contract` block of each product's target, plus the estate ownership keys. |
| `odcs` block: server, account, database, schema | Nothing in a declaration. Physical coordinates belong to a runtime binding. |
| `relations` verbs and bindings | Nothing. The estate graph is derived from the contracts products publish and the sources they declare. |
| `hashdiff_exclude` | The `data_vault` shape's target block. |

Work product by product, starting from what the estate publishes.

**Step 4.1: list the published relations.** Every relation a consumer reads, or a person
queries, is a product. Every relation that exists only as an intermediate step of computing
one of those is not: it becomes an occurrence inside the product that needs it, or a
translator-private relation the engine renders on its own.

**Step 4.2: give each product a label, a profile and a shape.**

- A relation fed directly by a source system is a `landing` product.
- A relation that conforms one landed extract is a `derivation` product.
- A relation that resolves identity across sources and applies survivorship is an
  `integration` product.
- A relation that combines two or more products is a `consolidation` product.
- A relation published for a named consumer is a `serving` product.

The shape describes the target's modelling form. Use `declared` for relations produced by
the composition and `canonical` for one relation per published entity. Use `dimensional`
for facts and dimensions, `ods` for a normalised relational form, and `data_vault` for
vault stores.

**Step 4.3: write the composition.** Order the pattern occurrences the product needs. The
profile says which are mandatory, which are optional and which are forbidden, so start from
the mandatory set and add what the product actually does. A pattern may occur more than
once: validation before and after transformation is the common case, and each occurrence
declares its own `stage`.

**Step 4.4: name the sources as contracts, never as tables.** A 0.5 model read a relation.
A 0.6 product reads a published contract, pinned to a major version, and declares what it
expects from it:

```yaml
sources:
  - contract: ecommerce.cartivo_customer@1
    expect:
      fields: [source_record_id, loyalty_id, email, customer_business_key]
```

At emission the engine compares that expectation with the producer's contract. Any
incompatibility stops emission, so the expectation must state the real dependency.

Where a product reads more than one source, add the combination as a sibling of `sources`,
and conform each source onto the schema it needs. A union stacks rows under one schema. A
merge puts columns side by side and declares its join keys. It also declares `inner`, which
keeps shared keys, or `outer`, which keeps every source row. Fields from an unmatched side
become optional. Neither form has a default:

```yaml
combine:
  method: union
```

```yaml
combine:
  method: merge
  keys: [customer_id]
  join: outer
```

Where a source's producer publishes several relations, name the one you read, as the
producer's shape names it and without the product prefix:

```yaml
sources:
  - contract: sales.order_star@1
    relation: fact_order_line
```

**Step 4.5: move the business logic.** Resolution and survivorship move onto the Data
Curation occurrence:

```yaml
  - pattern: data_curation
    entity: customer
    resolution:
      strategy: deterministic
      keys: [customer_loyalty_id, customer_normalised_email]
      record_key: customer_record_id
    survivorship:
      customer_email: first_non_null
      customer_status: most_recent
    precedence:
      source_column: customer_source_system
      recency_column: customer_as_of_date
      source_priority: [relatio, cartivo, mercaro]
```

Column renames and casts move onto a Schema Transform occurrence, one `{from, to, type}`
entry each. Derived columns move onto a Calculated Fields occurrence, each with a declared
type and either an `expression` or a `rule` naming a named rule. Reference joins move onto a
Data Enrichment occurrence, which reads a contract like any other source.

**Step 4.6: declare the publication patterns.** Data Contracts, Lineage Capture, Metadata
Capture, Schema Publish and Data Publish are mandatory in every profile. They take almost no
configuration, and they are what makes the product's contract, descriptor, lineage and
publication concrete and testable.

## 5. Hand-authored models

0.5 estates commonly kept some models hand-authored beside the generated ones. 0.6 does not
allow that: architecture section 13 forbids leaving a product hand-authored beside generated
products, and if the engine cannot generate one, the missing thing is a profile or a shape,
not the product.

For each hand-authored model, decide which it is:

- **It is a product.** Declare it. Most marts, dimensions, facts and canonical views are a
  `serving` or `derivation` product with the right shape, and a whole select body can go in
  the `declared` shape's optional `select` key while you convert the rest.
- **It is an intermediate step.** Fold it into the product that needed it, as an occurrence.
- **It is a business rule.** Make it a named rule, with its signature in the rule catalogue
  and its implementation in a macro.
- **It is nothing any more.** Delete it. A model that exists to feed a model that no longer
  exists is not a migration problem.

## 6. Regenerate, and prove the result

There is no byte-for-byte comparison with the 0.5 tree, and none is expected: 0.6 generates
different relations by different names. What you prove instead is that the new estate says
the right thing about the data.

```bash
ergasterion validate                # every declaration validates on its own
ergasterion emit-products           # one summary line per product, then the budgets
ergasterion emit-products --check   # a second run changes nothing
dbt deps --profiles-dir profiles
dbt parse --profiles-dir profiles --no-partial-parse -t duckdb
dbt build --profiles-dir profiles -t duckdb
```

Then add the assertions that make the result checkable by a person. Write them as singular
tests over the published relations, each stating an answer someone can verify: a total, a
count, a resolution that collapses a known set of records to one, a value the declared
authority supplies. These are what replace the comparison with 0.5.

## 7. Errors you should expect while converting, and what each one means

The engine refuses to guess. A conversion therefore produces a sequence of precise errors.
The common ones are:

- **A label has no translator-table entry for a pattern.** Your composition uses a pattern
  the label's entry does not cover. Add the entry to `estate.yml`.
- **A named rule has no implementation for a declared pair.** Either implement it for that
  translator and adapter, or stop declaring that adapter.
- **An inline expression does not parse, or a column does not resolve.** The message names
  the product, the occurrence and the position. An unresolved column usually means the
  schema visible at that occurrence does not yet carry it: check the ordering of your
  Schema Transform and Calculated Fields occurrences.
- **A declaration carries technology syntax.** A 0.5 expression survived the move. Convert
  it to inline SQL or to a named rule.
- **A source names none of several relations.** The producer's shape publishes more than one.
  Add the `relation` key.
- **A consolidated product declares no reconciliation.** Add the Data Validation occurrence
  whose rules reconcile its coverage back to its bases.
- **A forbidden pattern, or an occurrence out of order.** The profile the label admits does
  not allow it. Either the product belongs under a different profile, or the work belongs in
  a different product.

## 8. What you can stop maintaining afterwards

- The domain files, in full.
- Any hand-authored model that became a declaration.
- Any hand-written contract or descriptor: both are generated per product and schema-checked
  on every run.
- Any bespoke lineage export: product-level and field-level lineage come from the
  declarations, in the estate graph.
